## Données et permissions
Kinds : suggestion/bug/positive. États de traitement : reçu, à l’étude, planifié, traité, clos ; vocabulaire technique de suivi, pas promesse de réalisation. Admin peut changer ces états et retirer une suggestion. Les suggestions ne sont publiées qu’avec un titre/résumé saisis pour le partage ; bugs et retours positifs restent privés. L’interface invite l’admin à exclure identités/détails privés. Il n’existe pas de détection automatique garantissant l’anonymisation d’un texte libre ; relecture administrative nécessaire.

Le serveur ignore les identités, rôles, publication et compteurs forgés par l’émetteur. L’utilisateur lit seulement ses retours, l’admin les traite ; aucun propriétaire/requestId/liste de votants dans les réponses de lecture. Projection de suggestion : id, titre partagé, résumé partagé, statut, date, compteur et booléen de vote propre. Un vote maximum par clé de compte rôle/email, répétition sans incrément. Vote admin refusé ; aucune suggestion non publiée votable. Les votes sont conservés lors du retrait, sans purge. Les changements d’état n’engagent aucun achat, droit Premium ou calendrier de livraison.

Création protégée par requestId : même compte/contenu = même id ; contenu différent = 409. Une réponse réseau perdue ne fait pas perdre le brouillon ni changer la clé ; après succès le formulaire est vidé et les données relues. Les modifications ultérieures du brouillon créent une nouvelle demande explicite. Lecture d’erreur visible avec actualisation manuelle ; aucun polling.

Stockage : `feedback?` facultatif dans le même document DemoState. Les anciens états sans ce champ restent lisibles ; pas de deuxième backend/migration. Adaptateur Blobs CAS réutilisé pour les mutations hébergées, mais aucune preuve de persistance ou concurrence distante de CE module en l’absence de déploiement. Local : mémoire de test, perdue au redémarrage. Les preuves hébergées des réservations/messages/avis précédents ne sont pas extrapolées aux retours bêta.
